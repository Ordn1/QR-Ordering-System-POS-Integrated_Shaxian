## 1. Design principles

These govern every decision below. Follow them for any table added later.

### 1.1 Two classes of primary key

This is the single most important convention in this schema.

**Reference tables** — entities the restaurant *configures* and *manages*. They are finite, human-facing, and staff refer to them out loud and in print. These use a **formatted, human-readable string key**:

```
TBL-0001    tables
STF-0001    staff_accounts
CAT-0001    categories
MNU-0001    menu_items
APR-0001    apriori_rules
```

Format is invariably `PREFIX-NNNN` — a three-letter uppercase prefix, a hyphen, and a zero-padded four-digit sequence. Always exactly 8 characters. Four digits is deliberate: it never wraps for a single restaurant, and every ID column lines up at the same width in a query result, an admin table, or a printed report.

**Transactional tables** — records generated by activity. They accumulate without bound for as long as the restaurant operates. These use a **plain auto-incrementing integer key**:

```sql
BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

No prefix, no padding, no format. Formatting a key that will reach seven figures buys nothing and costs storage on every foreign key that references it.

Use `GENERATED ALWAYS AS IDENTITY`, not `BIGSERIAL`. Identity columns are the SQL-standard form, they cannot be accidentally overwritten by an explicit insert, and they are what modern PostgreSQL expects.

**Assignment:**

| Class | Tables |
|---|---|
| **Reference** (`PREFIX-NNNN`) | `tables`, `staff_accounts`, `categories`, `menu_items`, `apriori_rules` |
| **Transactional** (identity) | `sessions`, `session_devices`, `transactions`, `transaction_items`, `kitchen_queue`, `payments`, `analytics_events`, `priority_verification_log`, `audit_log` |

`apriori_rules` sits with the reference tables because it is a *catalog* — a finite rule set regenerated wholesale each night, browsable by the administrator. It is not an ever-growing event log.

### 1.2 Field sizes are chosen, never defaulted

Every `VARCHAR` length in this document was picked to fit the data it actually holds. **Do not substitute `VARCHAR(255)` anywhere.** A column sized to its content documents its own intent — `CHAR(60)` for a bcrypt hash tells the next reader exactly what lives there in a way `VARCHAR(255)` never will.

Likewise, use the **narrowest integer that fits**:

- `SMALLINT` (max 32,767) — quantities, queue positions, display order, calories, table numbers
- `INTEGER` — not needed anywhere in this schema
- `BIGINT` — identity primary keys and their foreign keys only

### 1.3 Use PostgreSQL properly

This schema is not a port of a generic design. Use the platform:

| Instead of | Use | Why |
|---|---|---|
| `VARCHAR` + `CHECK (col IN (...))` | **native `ENUM` types** | Enforced at the type level, self-documenting, 4 bytes |
| `VARCHAR(36)` for a UUID | **`UUID`** | 16 bytes rather than 36, natively validated |
| `JSON` | **`JSONB`** | Binary, indexable with GIN, faster to query |
| `TIMESTAMP` | **`TIMESTAMPTZ`** | Timezone-aware; the restaurant runs in Asia/Manila |
| `FLOAT` / `REAL` for money | **`NUMERIC(p,s)`** | Exact decimal — never use floating point for currency |
| `BIGSERIAL` | **`GENERATED ALWAYS AS IDENTITY`** | SQL-standard, safer |

### 1.4 Naming conventions

- Tables: `snake_case`, **plural** (`menu_items`, `sessions`)
- Columns: `snake_case`, **singular**
- Primary keys: `<singular_entity>_id` (`table_id`, `session_id`)
- Foreign keys: identical to the referenced primary key's name
- Booleans: `is_` / `has_` prefix (`is_active`, `is_host`)
- Timestamps: `_at` suffix (`created_at`, `completed_at`)
- Money: `_amount` suffix, always `NUMERIC`
- Enum types: `<concept>_enum` (`session_type_enum`)
- Indexes: `idx_<table>_<columns>` · Constraints: `chk_<table>_<rule>`

### 1.5 Migration policy

**Every schema change goes through an Alembic migration. No exceptions, ever.** No hand-run `CREATE TABLE`, no `ALTER TABLE` in a psql session, no SQLAlchemy `create_all()` in application code. The migration history is the schema's only source of truth. Every migration must have a working `downgrade()`.

## 2. Corrections to the source paper

The research paper's data dictionary contains errors inherited from earlier drafts. **This document supersedes it.** Implement what is written here.

| Paper says | Correct | Why |
|---|---|---|
| "PostgreSQL 3.x", "embedded", `ordering.db` | **Server-based PostgreSQL 15+** | `3.x` is a SQLite version number and `.db` is a SQLite file. Leftovers from an abandoned SQLite draft. PostgreSQL is a server; it has no embedded mode and no `.db` file. |
| `table_id VARCHAR(6)`, format `TBL-NNN` | **`VARCHAR(8)`, format `TBL-0001`** | `TBL-NNN` is 7 characters and does not fit in 6. Standardized to a 4-digit sequence across all reference tables. |
| `password_hash VARCHAR(255)` | **`CHAR(60)`** | A bcrypt hash is *exactly* 60 characters. 255 is a copied default. |
| `qr_token VARCHAR(36)` | **`UUID`** | Native type — smaller and validated. |
| `metadata_json JSON(1000)` | **`JSONB`**, unbounded | PostgreSQL does not length-bound JSON, and JSONB is indexable. |
| Table 16: `device_id BIGINT(36)` | **`device_id BIGINT` FK** + separate `device_token UUID` on `session_devices` | A length of 36 on a BIGINT is a UUID artifact. Resolved in §3.6. |
| Camera / age-detection / `privacy_log` references | **Do not implement** | The camera-based design was abandoned. See `ProjectOverview.md` §6.3. There is no biometric data anywhere in this schema. |

CREATE TYPE language_enum         AS ENUM ('en', 'fil', 'bis');

CREATE TYPE payment_method_enum   AS ENUM ('online', 'cashier');

**Note on `priority_status_enum` vs `session_type_enum`** — these are different things and must not be conflated:

All three of `senior`, `pwd`, and `pregnant` collapse into the single `priority` segment. `group` overrides regardless of declared status. See §3.5.

## 4. Formatted key generation

Each reference table gets a dedicated sequence and a `DEFAULT` expression, so the database generates IDs itself and application code never constructs one by hand.

```sql
CREATE SEQUENCE seq_tables        START 1;
CREATE SEQUENCE seq_staff         START 1;
CREATE SEQUENCE seq_categories    START 1;
CREATE SEQUENCE seq_menu_items    START 1;
CREATE SEQUENCE seq_apriori_rules START 1;
```

Applied as, for example:

```sql
table_id VARCHAR(8) PRIMARY KEY
    DEFAULT ('TBL-' || LPAD(nextval('seq_tables')::TEXT, 4, '0'))
```

Every reference table additionally carries a regex `CHECK` guaranteeing the format holds even on a manual insert:

```sql
CONSTRAINT chk_tables_id_format CHECK (table_id ~ '^TBL-[0-9]{4}$')
```

Use `VARCHAR(8)`, not `CHAR(8)`. PostgreSQL's own documentation advises against `CHAR(n)`: it is blank-padded, carries no performance benefit, and its padding causes subtle comparison bugs in client libraries. The regex `CHECK` enforces the fixed width far more strictly than `CHAR` ever would.

### 5.5 `apriori_rules`
Pre-computed association rules, regenerated nightly. Read at recommendation time and never written during a customer session.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `rule_id` | `VARCHAR(8)` | PK, `DEFAULT 'APR-'‖seq`, regex CHECK | `APR-0001` |
| `session_type` | `session_type_enum` | NOT NULL | The mining segment |
| `antecedents` | `JSONB` | NOT NULL | Array of `item_id` — the cart side |
| `consequents` | `JSONB` | NOT NULL | Array of `item_id` — what to suggest |
| `support` | `NUMERIC(6,4)` | NOT NULL, CHECK 0–1 | |
| `confidence` | `NUMERIC(6,4)` | NOT NULL, CHECK 0–1 | |
| `lift` | `NUMERIC(6,4)` | NOT NULL, CHECK > 0 | Only lift > 1.0 is useful |
| `generated_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | Batch run timestamp |

`antecedents` and `consequents` hold JSON arrays of `menu_items.item_id` strings, e.g. `["MNU-0001"]`. **This table has no foreign key to `menu_items`** — item references live inside JSON, which PostgreSQL cannot constrain. The nightly batch job is responsible for only emitting valid item IDs.

Indexes matter here. The 50 ms retrieval budget depends on them:

```sql
CREATE INDEX idx_apriori_segment_lift
    ON apriori_rules (session_type, lift DESC);

CREATE INDEX idx_apriori_antecedents
    ON apriori_rules USING GIN (antecedents);
```

The first serves "top 3 by lift within this segment"; the GIN index serves antecedent containment matching against the current cart.

⚠️ The paper's Table 19 lists a `rule_type` column but never defines its values. **It is omitted here.** Flag this — see §12.1.

## 6. Transactional tables

### 6.1 `sessions`
One customer's ordering interaction, from QR scan to checkout. Parent of nearly everything.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `session_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | |
| `table_id` | `VARCHAR(8)` | NOT NULL, FK → `tables` | |
| `started_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | |
| `ended_at` | `TIMESTAMPTZ` | NULL | NULL = still active |
| `declared_priority_status` | `priority_status_enum` | NOT NULL, DEFAULT `'standard'` | **Self-declared only** |
| `session_type` | `session_type_enum` | NOT NULL, DEFAULT `'standard'` | The Apriori segment tag |
| `group_mode` | `BOOLEAN` | NOT NULL, DEFAULT FALSE | TRUE once a 2nd device joins |
| `ui_mode_used` | `ui_mode_enum` | NOT NULL, DEFAULT `'standard'` | |
| `language_used` | `language_enum` | NOT NULL, DEFAULT `'en'` | |
| `accessibility_accepted` | `BOOLEAN` | NOT NULL, DEFAULT FALSE | |

**`session_type` is stored, not derived.** It is technically computable from `declared_priority_status` and `group_mode`, but the paper specifies it is written to the sessions table at the start of ordering, and the nightly Apriori job segments on it directly. Storing it also preserves the segment a transaction was actually mined under, even if the derivation rule later changes.

The write rule, applied at session start and again whenever a second device joins:

```
group_mode = TRUE                        → session_type = 'group'
declared_priority_status ≠ 'standard'    → session_type = 'priority'
otherwise                                → session_type = 'standard'
```

`group` takes precedence over `priority`.

**`declared_priority_status` is populated by the customer tapping a control. Nothing else may ever write it.** No inference, no detection, no camera. See `ProjectOverview.md` §6.3.

```sql
CREATE INDEX idx_sessions_table_active ON sessions (table_id) WHERE ended_at IS NULL;
```

A partial index — the "is this table currently in session?" lookup runs on every scan, and only open sessions matter.

### 6.2 `session_devices`
Every phone that has joined a table session. One row for a solo session; two or more for a group.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `device_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | Internal key |
| `session_id` | `BIGINT` | NOT NULL, FK → `sessions` ON DELETE CASCADE | |
| `device_token` | `UUID` | NOT NULL, UNIQUE, `DEFAULT gen_random_uuid()` | Client-facing handle |
| `joined_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | |
| `display_name` | `VARCHAR(30)` | NULL | Optional nickname |
| `is_host` | `BOOLEAN` | NOT NULL, DEFAULT FALSE | TRUE = opened the session |

**Resolving the paper's `device_id` / `device_token` confusion.** The paper's ERD references both, and Table 16 lists `device_id BIGINT(36)` — a length that only makes sense for a UUID. They are two distinct things and this schema keeps both:

- **`device_id`** — the internal `BIGINT` primary key. All foreign keys (`transaction_items`, `payments`) point at this.
- **`device_token`** — an opaque `UUID` the browser stores locally so a phone can re-identify itself after a refresh. Never used as a foreign key.

Splitting them keeps joins on a compact integer while giving the client a token that leaks nothing about how many devices the system has seen.

### 6.3 `transactions`
A completed or abandoned order. Parent of `transaction_items`, `payments`, and `kitchen_queue`, and the source table the nightly Apriori job reads.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `txn_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | |
| `session_id` | `BIGINT` | NOT NULL, FK → `sessions` | |
| `placed_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | |
| `gross_amount` | `NUMERIC(10,2)` | NOT NULL, CHECK ≥ 0 | Before tax & discount |
| `vatable_sales` | `NUMERIC(10,2)` | NOT NULL, DEFAULT 0 | Portion subject to 12% VAT |
| `vat_exempt_sales` | `NUMERIC(10,2)` | NOT NULL, DEFAULT 0 | Senior/PWD exempt portion |
| `vat_amount` | `NUMERIC(10,2)` | NOT NULL, DEFAULT 0 | 12% VAT collected |
| `discount_amount` | `NUMERIC(10,2)` | NOT NULL, DEFAULT 0 | Statutory discount |
| `net_amount` | `NUMERIC(10,2)` | NOT NULL, CHECK ≥ 0 | Final amount due |
| `item_count` | `SMALLINT` | NOT NULL, CHECK > 0 | Total units |
| `is_priority` | `BOOLEAN` | NOT NULL, DEFAULT FALSE | Eligible for priority queue |
| `queue_date` | `DATE` | NOT NULL, DEFAULT `CURRENT_DATE` | Business day |
| `queue_number` | `SMALLINT` | NOT NULL, CHECK > 0 | Daily rolling number |
| `status` | `txn_status_enum` | NOT NULL, DEFAULT `'pending'` | |
| `voided_by` | `VARCHAR(8)` | NULL, FK → `staff_accounts` | |
| `void_reason` | `VARCHAR(120)` | NULL | |
| `voided_at` | `TIMESTAMPTZ` | NULL | |

**The four tax columns are a legal requirement, not bookkeeping decoration.** RA 9994 and RA 10754 grant a 20% discount *with VAT exemption*, so the exempt portion must be recorded separately from the VAT-able portion for BIR compliance. Never collapse them into one total.

**`queue_date` is an addition to the paper.** The paper calls `queue_number` a "daily rolling queue identifier" but gives it nothing to roll against. Without a date, uniqueness cannot be enforced and yesterday's Q-006 collides with today's. Together they carry a genuine constraint:

```sql
CONSTRAINT uq_txn_queue_daily UNIQUE (queue_date, queue_number)
```

```sql
CREATE INDEX idx_txn_session   ON transactions (session_id);
CREATE INDEX idx_txn_status    ON transactions (status) WHERE status IN ('pending','preparing','ready');
CREATE INDEX idx_txn_placed_at ON transactions (placed_at DESC);
```

| `item_id` | `VARCHAR(8)` | NOT NULL, FK → `menu_items` ON DELETE RESTRICT | |

### 6.5 `kitchen_queue`
The live kitchen sequence. **This table is where the fairness-bounded priority queue actually lives.**

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `queue_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | |
| `txn_id` | `BIGINT` | NOT NULL, **UNIQUE**, FK → `transactions` | One queue slot per order |
| `queue_position` | `SMALLINT` | NOT NULL, CHECK > 0 | Live position |
| `priority_skips_used` | `SMALLINT` | NOT NULL, DEFAULT 0, CHECK ≥ 0 | **The fairness bound** — see below |
| `updated_by` | `VARCHAR(8)` | NULL, FK → `staff_accounts` | Crew member who last changed status |
| `entered_queue_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | |
| `prep_started_at` | `TIMESTAMPTZ` | NULL | |
| `completed_at` | `TIMESTAMPTZ` | NULL | |

**`priority_skips_used` is the single most important column in this schema.** It counts **how many times this order has been skipped by a later-arriving priority order** — so it is only ever non-zero on standard orders. Once it reaches the cap, the order becomes *protected* and no further priority order may pass it.

That is what makes the queue *bounded* rather than an unconditional cut-in-line privilege: **no standard order is ever delayed by more than the cap, regardless of how many priority orders arrive.** Without it, standard diners starve during senior-heavy periods and the implementation has failed its own research claim.

⚠️ Note the direction. An earlier draft defined this column as counting how many standard orders a *priority* order had advanced ahead of. That does not prevent starvation — each new priority order arrives with a fresh counter and skips the same standard order again, indefinitely. The counter belongs on the order being skipped. See `Algorithms.md` §2.2 for the full reasoning and §2.4 for a worked example.

`UNIQUE` on `txn_id` enforces the one-to-one: an order occupies exactly one kitchen slot.

```sql
CREATE INDEX idx_queue_active ON kitchen_queue (queue_position) WHERE completed_at IS NULL;
```

| `amount` | `NUMERIC(10,2)` | NOT NULL, CHECK > 0 | |
| `discount_applied` | `NUMERIC(10,2)` | NOT NULL, DEFAULT 0 | |
| `aggregator_ref` | `VARCHAR(50)` | NULL | PayMongo reference — online only |
| `status` | `payment_status_enum` | NOT NULL, DEFAULT `'pending'` | |
| `print_status` | `print_status_enum` | NULL | Cashier receipts only |
| `paid_at` | `TIMESTAMPTZ` | NULL | Set on settlement |

One-to-**many** from `transactions` is deliberate: a split bill produces one row per payer, and their sum must reconcile to `transactions.net_amount`. Enforce that reconciliation in the service layer.

**No card numbers, no cardholder credentials, no raw gateway payloads are ever stored here.** `aggregator_ref` holds an opaque reference and nothing more.

### 6.7 `analytics_events`
Every interaction event from the React client. **The raw feed for confusion detection** and the source for the admin dashboard's trigger-rate and recommendation-acceptance figures.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `event_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | |
| `session_id` | `BIGINT` | NOT NULL, FK → `sessions` ON DELETE CASCADE | |
| `event_type` | `event_type_enum` | NOT NULL | |
| `screen_id` | `VARCHAR(40)` | NULL | Where it happened |
| `occurred_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | |
| `metadata` | `JSONB` | NULL | Event-specific detail |

The first four enum values are the paper's four confusion signals. The three `recommendation_*` values are additions — the paper's dashboard reports "recommendation acceptance rates," which cannot be computed unless shown/accepted/dismissed are logged.

`metadata` carries per-event detail: `{"item_id": "MNU-0001", "dwell_seconds": 52}`.

```sql
CREATE INDEX idx_events_session_time ON analytics_events (session_id, occurred_at DESC);
CREATE INDEX idx_events_type         ON analytics_events (event_type);
```

The first index serves the hot path — "have two signals fired concurrently in this session?" — and must exist for the 50 ms budget to hold.

**This is the highest-volume table in the schema.** It grows on every scroll and tap. Plan a retention policy; raw events older than the analysis window can be aggregated and pruned.

### 6.8 `priority_verification_log`
An audit trail of every priority-status declaration. **This table replaces the abandoned camera-based `privacy_log` entirely.**

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `log_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | |
| `session_id` | `BIGINT` | NOT NULL, FK → `sessions` | |
| `declared_status` | `priority_status_enum` | NOT NULL, CHECK ≠ `'standard'` | |
| `id_presented` | `BOOLEAN` | NOT NULL, DEFAULT FALSE | Was a physical ID shown? |
| `id_last4` | `CHAR(4)` | NULL, CHECK `~ '^[0-9]{4}$'` | **Last four digits only** — see below |
| `cardholder_name` | `VARCHAR(80)` | NULL | Name printed on the ID |
| `issuing_lgu` | `VARCHAR(50)` | NULL | City/municipality that issued it |
| `verified_by` | `VARCHAR(8)` | NULL, FK → `staff_accounts` | Which crew member checked |
| `verified_at` | `TIMESTAMPTZ` | NULL | |
| `discount_eligible` | `BOOLEAN` | NOT NULL, DEFAULT FALSE | Qualifies under RA 9994 / 10754 |

**Contains no images and no biometric data of any kind.** It records text fields transcribed from a physical card that a staff member looked at with their eyes. Its purpose is to give the priority queue and automatic discount a verifiable compliance record for BIR audit.

**The full OSCA / PWD card number is never stored.** An earlier draft of this schema held `id_number VARCHAR(30)`. It is replaced by `id_last4` — a four-digit fragment — on the principle that **data not collected cannot be breached**.

The compliance record's actual job is to prove a discount was applied against a verified declaration. That needs to establish *that* an ID was presented, *who* verified it, *when*, and enough to tell one declaration from another. It does not need the full number. Reducing the column eliminates the highest-risk field in the database outright and satisfies the Data Privacy Act's data-minimization principle directly, rather than mitigating the risk with encryption after the fact.

`id_last4` and `cardholder_name` remain the most sensitive columns in the database. Both are optional, both are masked server-side at display time, and both are exposed only to authenticated staff — never on a customer-facing endpoint. See `Security.md` §5.3 and §5.4.

### 6.9 `audit_log`
A permanent, append-only record of staff actions carrying financial or data consequences. Required by `Security.md` §6.3.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `audit_id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` | |
| `staff_id` | `VARCHAR(8)` | NULL, FK → `staff_accounts` | NULL for system-initiated actions |
| `action` | `VARCHAR(40)` | NOT NULL | `price_change`, `txn_void`, `login_failed` |
| `entity_type` | `VARCHAR(40)` | NOT NULL | `menu_item`, `transaction`, `staff_account` |
| `entity_id` | `VARCHAR(20)` | NULL | Accommodates both key classes |
| `before_state` | `JSONB` | NULL | Prior values of changed fields only |
| `after_state` | `JSONB` | NULL | New values of changed fields only |
| `ip_address` | `INET` | NULL | PostgreSQL native type |
| `occurred_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | |

```sql
CREATE INDEX idx_audit_staff_time ON audit_log (staff_id, occurred_at DESC);
CREATE INDEX idx_audit_entity     ON audit_log (entity_type, entity_id);
```

**This table is append-only.** There is no update path, no delete path, and no UI affordance to edit it. An audit trail a staff member can alter is not an audit trail. Enforce it at the database level:

```sql
REVOKE UPDATE, DELETE ON audit_log FROM app_user;
```

`entity_id` is `VARCHAR(20)` rather than a foreign key because it must hold both key classes — `MNU-0001` from a reference table and `48213` from a transactional one. A polymorphic reference cannot carry a foreign key constraint, so integrity here is the service layer's responsibility.

**`before_state` and `after_state` never contain a password hash, a token, or personal data.** They record which fields changed and to what — not the sensitive values themselves. A diff of a staff account records that `role` changed from `service_crew` to `admin`; it never records `password_hash`.

`staff_id` uses `ON DELETE RESTRICT` like every other staff reference. Deactivate accounts; never delete them. An audit entry whose actor has vanished is worthless.

`ip_address` uses PostgreSQL's native `INET` type rather than `VARCHAR` — it validates the address, handles IPv4 and IPv6 in one column, and supports subnet queries.

## 7. Relationship summary

```
tables ──1:N──> sessions ──1:N──> session_devices
                   │                     │
                   ├──1:N──> transactions │
                   │             │        │
                   │             ├──1:N──> transaction_items ──N:1──> menu_items
                   │             ├──1:1──> kitchen_queue              │
                   │             └──1:N──> payments                   │
                   │                          │                       │
                   ├──1:N──> analytics_events  └──(device_id)─────────┘
                   └──1:N──> priority_verification_log

categories ──1:N──> menu_items

staff_accounts ──1:N──> kitchen_queue (updated_by)
               ──1:N──> priority_verification_log (verified_by)
               ──1:N──> transactions (voided_by)
               ──1:N──> audit_log (staff_id)

apriori_rules  ── standalone, no FK constraints
audit_log      ── staff_accounts only; entity_id is polymorphic, unconstrained
```

**Delete behavior:**

| Relationship | Rule | Why |
|---|---|---|
| `sessions` → `session_devices` | `CASCADE` | Devices are meaningless without their session |
| `sessions` → `analytics_events` | `CASCADE` | Same |
| `transactions` → `transaction_items` | `CASCADE` | Line items cannot outlive their order |
| `transactions` → `payments` | `CASCADE` | Same |
| `categories` → `menu_items` | `RESTRICT` | Never silently orphan the menu |
| `menu_items` → `transaction_items` | `RESTRICT` | **Never delete an item referenced by history** — set `is_available = FALSE` instead |
| `staff_accounts` → anything | `RESTRICT` | Preserve the audit trail; deactivate rather than delete |
| `audit_log` → nothing | **No delete path at all** | Append-only; see §6.9 |

**Menu items and staff accounts are soft-deleted, never hard-deleted.** Both are referenced by historical records that must remain intact for audit.

### 8.1 Seeding `apriori_rules` — match the paper

The paper works a specific example end to end, and **the seeded rules must reproduce it exactly** so a live demo agrees with the manuscript a panelist is reading:

> Priority segment, T = 3 transactions. A = {Fried Chicken}, B = {Rice}.
> Support(A) = 0.67 · Support(B) = 0.67 · Support(A∪B) = 0.67
> **Confidence = 1.00 · Lift = 1.49**

Seed that rule verbatim under `session_type = 'priority'`:

```json
{
  "rule_id":      "APR-0001",
  "session_type": "priority",
  "antecedents":  ["MNU-0001"],
  "consequents":  ["MNU-0002"],
  "support":      0.6700,
  "confidence":   1.0000,
  "lift":         1.4900
}
```
*(where `MNU-0001` = Fried Chicken and `MNU-0002` = Rice)*

Then seed the remaining rules so that **the same item pair carries a different lift in different segments.** This is the entire point of demographic segmentation — if every segment returns identical suggestions, the capstone element demonstrates nothing. Make the difference visible: priority sessions should skew toward rice and soup pairings, group sessions toward buckets and platters.

All seeded rules must have `lift > 1.0` and reference `item_id` values that actually exist.

## 9. Performance requirements

Two of the paper's non-functional targets fall on this schema:

| Target | Requirement | How it is met |
|---|---|---|
| Rule lookup | **< 50 ms** | `idx_apriori_segment_lift` + GIN on `antecedents` |
| POS injection | **< 1.5 s** after checkout | Indexed FK writes; async commit |

**Connection pooling** — configure the SQLAlchemy async engine with `pool_size=10`, `max_overflow=20`. The system must hold 30+ concurrent devices per the hardware spec.

**Transaction isolation** — checkout must be atomic. Writing `transactions`, `transaction_items`, `kitchen_queue`, and `payments` happens in **one database transaction**. A partial checkout that produces an order with no queue slot is a corrupt state.

**Queue-number assignment races.** Two phones checking out simultaneously must never receive the same `queue_number`. Use a per-day sequence or `SELECT … FOR UPDATE` on the day's counter. The `UNIQUE (queue_date, queue_number)` constraint is the backstop, but do not rely on catching the violation — assign correctly in the first place.

## 10. Data privacy

Per RA 10173 (Data Privacy Act of 2012):

**The database stores no biometric data of any kind.** No images, no facial data, no age estimation, no camera output. This is architectural, not configurable.

The only personally identifying columns in the entire schema are `priority_verification_log.id_last4` and `.cardholder_name`, both optional, both transcribed by hand from a physical card the customer chose to present, both masked server-side at display time, both restricted to authenticated staff endpoints.

**No full government ID number is stored anywhere in this database.** See §6.8 — the ID column holds four digits, by design rather than by accident.

Customers are never required to create an account. A session is anchored to a table and a device token — not to a person.

## 12. Questions and clarifications — REQUIRED BEFORE YOU BUILD

**Do not begin implementation assuming this schema is complete.** It is derived from an in-progress research paper whose data dictionary contains known errors — several are corrected in §2, and others may remain.

A wrong assumption baked into a schema is the most expensive kind of mistake in this project: it propagates into models, endpoints, UI, and seed data, and unwinding it means a migration plus a rewrite. **Ask first.**

### 12.1 Known open items — raise these, do not guess

1. **`rule_type` in `apriori_rules`.** The paper lists the column but never defines its permitted values. Omitted here. Confirm whether it is needed, and if so what it holds.
2. **POS integration tables.** The partner restaurant's existing POS schema is undocumented. No POS-side tables are defined here. Integration cannot be designed until that schema is supplied.
3. **Optional customer accounts.** The paper mentions a returning customer's previous-order history via "an optional account," but no `customers` table exists in the data dictionary. Confirm whether this is in scope — it would add a table and a nullable FK on `sessions`.
4. **Menu content.** Whether the real partner-restaurant menu is available, or seeds should use representative placeholders.
5. **VAT rate.** 12% is assumed throughout. Confirm it should be a configuration value rather than a hardcoded constant.
6. **Retention policy for `analytics_events`.** The highest-volume table in the schema, with no stated retention window.

### 12.2 Raise anything else that is

- Ambiguous, or open to more than one reasonable reading
- Contradictory between this file and `ProjectOverview.md`, the paper, or another document
- Structurally required but absent — a column, constraint, or relationship you would otherwise have to invent
- In tension with a stated performance target
- Seemingly at odds with §10 or with `ProjectOverview.md` §6 — **treat those as hard stops and always ask**

**Do not silently invent columns or tables.** If you must proceed past an ambiguity, state the assumption prominently rather than burying it in a migration.
